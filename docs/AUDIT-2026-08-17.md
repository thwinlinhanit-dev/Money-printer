## The one thing that matters most

**The daily gate has been blind since 08-13 (4+ days). No `.json` scorecards
exist for 08-13, 08-14, 08-15, or 08-16. The last archived verdict is
`2026-08-12.json` (DIRTY).**

This is the same failure mode the 08-08 audit flagged ("gate unevaluated for
~3 days"), now self-inflicted by the tooling the 08-13 commit shipped.

**Root cause chain:**
1. Commit `b8296d3` (08-13 12:18 UTC) added `sim/src/bin/mp-determinism.rs`
   with a `now_ns()` helper that calls `SystemTime::now()` — used solely to
   stamp the determinism artifact's `ts_ns` metadata field.
2. The guardrails script (`ops/ci/guardrails.ps1`) scans all `sim/**/*.rs` for
   `(SystemTime|Instant|Utc|Local)::now(`. Two files are on the existing
   allowlist (`core/src/wall_clock.rs`, `storage/src/historical_download.rs`)
   because they are sanctioned clock readers. `mp-determinism.rs` is not.
3. The daily pipeline (`daily_pipeline.ps1`) runs guardrails **first** and
   **exits 1** (fail-closed) on any violation — before the scorecard is
   written or archived.
4. Every 00:05 UTC pipeline run since 08-14 dies at this step.
   `pipeline.log` shows: `GUARDRAIL FAIL: PD-3/CONV-5` at 08-14 03:03,
   08-15 00:05, 08-16 00:05, 08-17 14:23.

**The wall clock in mp-determinism is a guardrail false positive** — the
artifact timestamp is metadata (same as `core/src/wall_clock.rs` which
provides the injected clock, and `storage/src/historical_download.rs` which
stamps archive rows). Two compliant fixes exist:
- Add `sim/src/bin/mp-determinism.rs` to the guardrails allowlist with a
  justification comment (parallels the two existing exceptions).
- Restructure so the pipeline injects the timestamp via `--ts-ns` (the
  `cmd_storage_budget` pattern already does this).

The **pipeline-stale watchdog** (OPS-17, `MoneyPrinterPipelineStale` Windows
task at 00:15 UTC) should be firing P1s about the missing scorecard — verify
on the host that ntfy/webhook delivery is active.

**Impact on the streak:** The promotion streak is **0/7** and cannot
progress until this is fixed. Even after fixing: 08-09 was the only
CLEAN day (coverage 0.9984); 08-10 (0.983), 08-11 (0.9935, close but
below 0.995), 08-12 (0.957 + 3 stale bursts + 3361s worst gap) are all
DIRTY. The ~3h20m periodic WS burst on the Windows VPN path persists.

### F4 — [P2] 08-15 BTC coverage regression (0.847)

**Severity:** P2 (data quality, gate blocked regardless)

The 08-15 BTC recording shows 0.8472 coverage — a significant regression
from 08-14's 0.9705. The burst files show multiple zero-count intervals
throughout the day. This is NOT a guardrails issue — it is a real data
quality problem. Investigate the BTC collector on 08-15 (was it
restarted? VPN drop? Hyperliquid-side issue?).

**Root cause (pinned 2026-08-18 from collector trace + watchdog log +
Windows System event log):** the 12,589 s worst gap is a host power-off,
not a venue or VPN event. Event 1074 at `11:17:18Z` — `Explorer.EXE`
initiated an unplanned power-off — then sleep `11:17:23Z → 14:23:42Z`
(Power-Troubleshooter); the collector's last trace line is `11:17:20Z` and
data resumes `14:27:12Z` after a fresh process (instance lock) reconnects.
Contributing: the WS egress path's DNS failed all day (6,422× os error
11001 "No such host is known", 07:22Z–23:54Z, plus 181–209× HTTP 502 at
08:04Z) — those drive the 12 zero-count bursts and the 10:54Z stream-stale
that starts the big hole. Amplifier: the collector's COL-1 backoff resets
on every TCP "connect" that succeeds while hostname resolution fails, so
the loop ran 2–3 attempts/s for 23 min (thousands of WS task ends; the
watchdog's respawns hit the same DNS wall). Coverage is span-based
(`1 − Σgaps/span`, storage::audit), so most nightly power-offs truncate
the UTC day at its tail and stay ~1.0; 08-15 was the case where the
machine was powered back on the same UTC day, making the hole interior.
Operational lesson: the recorder host power-cycles almost nightly (1074
on 07-14…08-16); the 0.995 bar cannot be met reliably while that
continues — either keep the host on (power settings) or move the
hyperliquid recording to the always-on VPS and retire the Windows A-B
leg (bringup §6 handoff).
