## HIGH

### A-1. Retention auto-deletes raw logs with no compact proof — `daily_maintenance.sh:205-221`, `daily_pipeline.ps1:753-772`
The Zero-Cost retention block runs (under `ZERO_COST=1`):

```bash
rm -f "$old_file"
done < <(find "$RAW_DIR" -maxdepth 1 -name '*.log' -type f -mtime +"$RETENTION_DAYS" -print0 ...)
```

The only guard is file age. There is:
- **no check** that a compacted Parquet (hash-verified per STO-8 `source_log_hash`)
  exists for the `(venue, date, symbol)` being deleted — the repo's own
  comment on the block even quotes W-6 (“never auto-delete without
  hash-verified compact proof”) and then does exactly that;
- **no scoping to gate recordings**: compaction (step 2) loops only over
  `$RECORDINGS` (HL BTC/ETH under Zero-Cost), but the sweep matches every
  `*.log` in `data/raw` — Bybit swing logs, whale/positions logs, macro logs
  recorded by the optional swing path are deleted 14 days after capture with
  no Parquet ever written for them;
- **a permanent-loss window for unclean days**: when yesterday's scorecard
  is dirty, the pipeline exits at the promote gate (`daily_maintenance.sh`
  `exit 1`) *before* compaction, so that day's raw is never compacted; two
  weeks later, on the first clean day, retention deletes it — no Parquet,
  no archive, no manifest. This is the C-2 failure mode (delete raws without
  verified compact proof) made automatic, on the free-tier failure patterns
  (intermittent sub-0.95 coverage) the mode explicitly expects.

The Windows twin (`daily_pipeline.ps1:753-772`) has the same shape against
`data\raw`. Deletions are only visible as `pipeline.log` lines; nothing
records *what* was deleted for later audit.

**Suggested fix:** before `rm`, verify a matching compacted artifact exists
for that venue/date/symbol (or move to a `data/raw-trash/` staging dir with a
manifest + second-pass delete); scope the sweep to the compacted recording
set; skip deletion for logs whose date has no passing INT-4 scorecard.

### A-2. `daily_pipeline.ps1` silently flips the Windows host into Zero-Cost (destructive) mode by default — `ops/scripts/daily_pipeline.ps1:152-160`
```powershell
if (-not $env:ZERO_COST) { $env:ZERO_COST = "1" }
if ($env:ZERO_COST -eq "1") {
    if ($Recordings.Count -eq 0) { $Recordings = @("hyperliquid:BTC", "hyperliquid:ETH") }
    $RequiredStreams = @("trade", "funding", "mark_price", "open_interest")
    ...
```

`ZERO_COST` defaults to **1** whenever the env var is unset — the normal case
for a Windows Scheduled Task, which does not inherit the shell environment.
An existing full-mode deployment therefore silently:
1. narrows its required/gated recordings to HL BTC+ETH (Bybit/other raws are
   still collected but never gated or compacted), and
2. starts deleting `data/raw/*.log` older than 14 days (A-1), on the machine
   the docs designate as secondary/cold storage with indefinite retention.

Nothing warns that destructive semantics just turned on. The comment says the
default targets “the VPS”, but the same script (and default) runs on the PC.
**Suggested fix:** require an explicit opt-in (`ZERO_COST=1` in the task/env,
or refuse to delete when the host is not the VPS), and log loudly when
deletion is armed.

## MEDIUM

### A-3. HEAD commit `a0335b4` does not compile `mp-collector` (E0063)
The Zero-Cost hardening commit added `backoff_base_ms`/`backoff_cap_ms` to the
collector config structs and reads them at `mp-collector.rs:931-936`, but the
CLI args builder (struct literal ending `swing_only: ...` at
`mp-collector.rs:185`) was never given the two fields. A clean checkout of
HEAD fails to build the binary (missing-field error). The uncommitted working
tree adds exactly `backoff_base_ms: None, backoff_cap_ms: None` (plus a
shadowing-rename cleanup), which is why every local check passes. **The fix
must be committed — HEAD as pushed is red.**

### A-4. `collectors/src/multisym.rs` (702 lines) is dead code
The spec 032 fan-out machinery — `resolve_symbols`, `acquire_locks_all_or_nothing`,
`WriterTable`, `bybit_frames_for_symbols`, and the `monotonicize` helper — is
referenced by no binary (`grep` over `collectors/src/bin/*.rs` finds nothing).
Zero-Cost Mode runs N single-symbol processes instead. Clippy confirms:
`field symbol is never read` (multisym.rs:137), `function meta is never used`,
`unused variable: eth` (multisym.rs:619). Either wire `--symbols` into
`mp-collector` (MSC-1..10) or mark the module/feature clearly as not-yet-wired
— as committed, it is 700 lines of untested-in-production surface that looks
implemented.

### A-5. `MarketProfilePoc` nondeterministic tie-break (PD-3) — `features/src/catalog.rs:949-959`
```rust
let mut profile: std::collections::HashMap<i64, f64> = ...;
...
profile.iter().max_by(|a, b| a.1.partial_cmp(b.1).unwrap_or(...))
```
POC is the argmax over a `HashMap`; on volume ties (common at the very fine
bucket granularity, see A-6) iteration order is per-process randomized, so
the emitted POC price differs run-to-run for identical input. `MarketProfileVah`/
`Val` sort into a `Vec` first (deterministic), but POC does not. Latent today
(`enabled: false` default, spec 049 Draft) — but the moment footprint signals
are enabled, the daily MOD-9 determinism replay can fail spuriously (or worse,
a feature value in the decision log is not reproducible). Fix: `sort_by` the
buckets and take the first max, matching VAH/VAL.

### A-6. “ATR-based” market-profile buckets are not ATR-based — `features/src/config.rs:784-785`, `catalog.rs:940-958`
`market_profile_bucket_atr` is documented as “Bucket size as multiple of ATR”
(default 0.5) and spec 049 says “Bucket size: ATR-based (default 0.5 ATR)”.
The implementation never computes ATR: `bucket_size = self.bucket_atr` is used
directly as an **absolute price width** (`(mid / bucket_size).floor()`). With
the default, BTC prices are bucketed at $0.50 — ~1000× finer than 0.5×ATR,
which is exactly what makes the A-5 tie problem reachable, and a strategy
tuned to “0.5 ATR buckets” gets different behavior per instrument/timeframe.
Either compute ATR (× multiplier) or rename the config and amend spec 049 to
say “absolute price width”.

### A-7. Zero-Cost “stale bursts are warnings only” is not what the code does — `mp-ops.rs:613-660`
`docs/ZERO_COST_MODE.md:120`, spec 024, and the `promotion_verdict_zero_cost`
docstring all say stale bursts are a warning under Zero-Cost and the
burst-free window condition is skipped. The implementation keeps calling
`check_promotion_n(...)` (mp-ops.rs:654), which still applies the burst-free
window condition to `stale_bursts`. The inline comment even acknowledges the
window “still fires”. Net effect is *stricter than documented* (safe
direction), but on a free-tier VPS a 14-day window with zero stale bursts may
never be met, and operators chasing the docs will misread why promotion is
stuck. Make the behavior match the docs (skip the window in zero-cost) or fix
the three documents.
