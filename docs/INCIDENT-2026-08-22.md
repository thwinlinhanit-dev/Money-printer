# INCIDENT 2026-08-22 — Promotion gate blind to schema-4 recordings

**Impact:** Every VPS nightly scorecard from 2026-08-19 through 2026-08-21
reported `event_count: 0, coverage: 0.0` for ALL recordings → permanent
DIRTY verdicts. The Phase-0 promotion streak silently read zero while the
recorders were actually producing clean data (hyperliquid BTC/ETH ran at
coverage 1.0 on those days). No alert fired: the pipeline-stale dead-man
only checks that a scorecard EXISTS, not that its numbers are plausible.

**Detection:** 2026-08-22, manual VPS review during swing-set rollout —
scorecard JSONs showed zeros while the same day-files were visibly growing
(hundreds of MB/day), and a fresh scorecard completed in ~5 s (impossible
for multi-GB audits).

**Root cause:** The `/opt/money-printer/bin/mp-ops` installed by
`deploy_schema4.sh` (2026-08-18) rejected event-log schema version 4:
`mp-ops audit` returned `legacy_or_malformed: unsupported event schema
version 4` on every recording written by the same deploy's collectors.
`/opt/money-printer/bin/mp-audit` from the SAME deploy decoded the identical
files correctly (432k events, CLEAN), so the defect was specific to mp-ops's
audit path in the 08-18 source snapshot. Rebuilding mp-ops from the current
tree fixed it with no code change — the divergence inside that snapshot
(ops-local decoder vs the core `LogReader`) is unverified post-mortem because
the old binary was replaced before comparison.

Aggravating factor: the nightly Windows drains had been failing (host asleep
at the 01:00 UTC window; wake-catchup runs died with `0xC000013A`), so closed
day-files stayed on the VPS and every night re-audited them into fresh false
DIRTY verdicts.

**Resolution (2026-08-22):**
1. Staged current sources into `~/mp-build`, rebuilt `-p mp-ops`
   (9m23s on the 2-vCPU box), reinstalled. Live scorecard immediately read
   real numbers (469,039 events, coverage 1.0, clean).
2. Backfilled TRUE scorecards for 2026-08-10..21 from the Windows master
   corpus (`data/scorecards/*.json`, sha256-identical sources) and installed
   them on the VPS. Honest record: Aug 13 clean; Aug 14–17 dirty (the
   VPN/Wi-Fi stale-burst era); **Aug 18–21 clean ⇒ streak = 4/7**, first
   break 08-10, burst day flagged 08-15 (window condition restarts on any
   burst, so the qualifying zero-burst window begins at the next burst-free
   run).
3. FRED macro leg enabled same day (separate change, see
   `docs/SWING_DATA_PLAN.md`).

**Lessons / follow-ups:**
- A gate that only proves "a scorecard exists" is not a health check.
  Plausibility guard: an all-zero `event_count` across every recording while
  collectors heartbeat should itself be an anomaly signal (backlog candidate).
- Version-skew regression test: feed a schema-current log fixture through
  `mp-ops scorecard`'s audit path asserting `event_count > 0` (`ops_slice`)
  so a reader/writer split can never ship again (BACKLOG).
- Deploys that rebuild SOME binaries must smoke-test the pair they split:
  after deploy_schema4, one command reading today's log through BOTH
  `mp-collector`→file→`mp-ops audit` would have caught this on 08-18.
