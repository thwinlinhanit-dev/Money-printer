## New findings (current state)

### Critical
None — nothing enables remote compromise of funds on the default (loopback,
non-live) configuration.

### High
1. **`opsd` HTTP surface has no authentication.** `ops/src/bin/opsd.rs:25–57`
   dispatches `GET /status` and `POST /beat/{process}` with zero token/header
   check. Any local (or `--bind`-widened remote) peer can refresh beats and keep
   the dead-man silent, defeating spec-009 alerting-on-absence. The 08-02/08-03
   docs overstate this ("requires a header token").
2. **`opsd` is single-threaded with a blocking, timeout-less `read`**
   (opsd.rs:26–29, 68–77). One peer that connects and sends nothing stalls the
   dead-man monitor forever — exactly the silent-death it exists to catch.
3. **P1 alert egress is dead code.** `ops/src/alert.rs:193 post_p1_webhook` is
   implemented but never called: opsd only `tracing::warn!`s (opsd.rs:39–41) and no
   binary reads `MP_OPS_P1_WEBHOOK`. The P1 phone/webhook channel cannot fire in
   any shipped binary. (Owner-gated is a *decision*; currently it is *silently
   dead*, which is worse.)
4. **`storage/src/promotion.rs` (7-day promotion gate) is orphaned** — not wired
   into the library or any CLI; and the compactor does not enforce the INT-4
   quarantine gate at cold-store ingress. Spec-024's integrity promise is not yet
   enforced where data enters the cold store.
5. **Risk gate RG-0 validation is incomplete (C2 partial).** `risk/src/gate.rs:128–137`
   validates `qty/price/mark/contract_multiplier` but **not**
   `current_position_qty / gross_exposure_notional / strategy_daily_pnl /
   portfolio_daily_pnl`, so RG-4/5/8/9 (`NaN >/= <` comparisons, gate.rs:165/177/189/193)
   remain NaN-bypassable at the gate boundary. Mitigated upstream (sim validates
   intents, sizing zeroes non-finite), but the gate is documented as a standalone
   paranoid boundary and does not defend itself.

### Medium
6. **guardrails.sh is POSIX/Linux-only** (`ops/ci/guardrails.sh:1`) and cannot run
   on the native Windows host that actually launches the collectors — mechanical
   PD enforcement is absent on the operational host.
7. **watchdog spawn is a shell-injection surface.** `ops/watchdog_collectors.ps1`
   builds `--symbol $Sym` args with `UseShellExecute=$true` and no quoting/allowlist
   (watchdog:88–94). Default BTCUSDT/ETHUSDT are benign; operator-supplied symbols
   are not validated.
8. **REST reseed busy-spins with no backoff** (`collectors/src/bin/mp-collector.rs:490–508`)
   on persistent failure — log spam during the exact disruption that causes gaps.
9. **P1 webhook is cleartext-only and refuses https** (`alert.rs:203–208`) — the
   money-at-risk channel is sent in the clear.
10. **sim IntentId collisions across strategies** (two strategies minting
    `IntentId(1),2,…` would misattribute fills) — latent, masked by single-strategy
    design (sim/src/engine.rs:116–118).
11. **L0 always-fill is the most optimistic rung but labeled `FillOptimism::None`**
    and not stripped by G1 (sim/src/fills.rs:181).

### Low / hygiene
- `collectors/src/bin/inspect_data.rs:38` `unwrap()` with no CONV-13 justification
  comment (provably safe — `read_dir`).
- guardrail clock-scan doesn't cover `oms/ collectors/ ops/ llm/` crates.
- `FeatureUpdate` keeps a per-emit heap `name: String` (spec 023 FEA-19 no-allocation
  partly unmet — acknowledged tradeoff for strategy self-filtering).
- `hit_journal` "reads date once at construction" doc comment is inaccurate — it
  reads the injected clock per record (mechanism is fine; comment wrong).
- `feature_store` crash-window idempotency gap (orphaned empty `ver=N` dir); compactor
  manifest `created_ts_ns` is non-byte-identical across re-runs.

## Verdict
The system is in genuinely healthy shape and **builds/test green**. All Critical and
most High findings from the 08-02 audit are verified fixed and tested. The remaining
issues are concentrated and fixable: the opsd auth/timeout gap and the dead P1 egress
(ops layer), the orphaned promotion/quarantine wiring (data integrity), the
incomplete gate RG-0 finiteness check (risk hardening), and a handful of labeling /
portability / hygiene items. None of them currently puts recorded data or funds at
risk on the default, non-live configuration — but the opsd token claim should be
corrected and the ops layer hardened before this system is relied upon to alert on
money-at-risk conditions.
