Guard against partial transfers: PER-FILE ssh|tar streams (`cmd /c` doubled-quote pipe; `~/vps_drain_pull.sh` include-list form streams exactly one rel) into `data\.vps-drain-staging`, per-file sha256+size verification against `~/vps_drain_list.sh`, land into `data/raw` only after verify, `~/vps_drain_release.sh` re-hashes each file right before deletion (changed file = skipped, never deleted). Slow-link resilience (2026-08-18): a dropped stream fails only that file — ssh/tar stderr is captured into `vps_drain.log` on failure (a drop exits non-zero, or yields an empty/absent stream that the post-transfer check detects and logs), verified staging copies from a failed run are REUSED across runs (resume; partial copies are re-pulled), and a transfer drop is exit 1 (partial) so the verified files still land+release; the exit-2 nothing-released contract is reserved for genuine size/hash mismatches (staged evidence kept). Slow-link economy (2026-08-16): the master corpus + manifest are consulted BEFORE the pull (`~/vps_drain_pull.sh` takes an include list) — byte-identical release re-attempts and KNOWN A-B collisions (latest manifest entry action=collision with the same VPS sha256) are never re-transferred, so the slow link moves only genuinely new closed days; the master-side hash stays authoritative (a deleted master file re-pulls, no stale skip). Collision policy (A-B overlap): a name already in `data/raw` with different content is NEVER overwritten or released (the Windows host's own recording wins until the handoff); identical = already landed, release the VPS copy. `-NoRelease` = land+verify only; `-Register` daily 01:00 UTC task `MoneyPrinterVpsDrain` (after the 00:05 gate and 00:30 backup); manifest `data/vps_drain_manifest.jsonl` (one entry per candidate with `action` landed/collision/missing and per-file `release` released | skipped:<reason> | ssh_failed | no_release | kept — `kept` = A-B collision, VPS copy stays by design; a transfer that never landed also records `transfer_error: transfer_failed`). Release-leg fix 2026-08-16: `~/vps_drain_release.sh` self-elevates (mp-egress → google-sudoers NOPASSWD; `data/raw` is printer-owned 755, so every nightly release since shipping aborted on `rm: Permission denied`, and PS 5.1 EAP=Stop turned that remote stderr into a terminating error that skipped the manifest — `vps_drain.ps1` now overrides EAP around the release ssh and checks `$LASTEXITCODE` so connection failures stay loud (exit 1, never a silent 0). The list phase uses the SAME override pattern (audit 2026-08-17: a transient ssh stderr line must not abort before the manifest is written); manifest timestamps parse with InvariantCulture + RoundtripKind (audit 2026-08-17, culture-safe))

## Local Contracts

- Collector watchdog (RETIRED 2026-08-18 §6 handoff — task disabled, no Windows collector runs; the bullets below document the kept script for rollback):
- Collector watchdog uses `Spawn-Process` with `UseShellExecute=true` for full process detachment
- A named local mutex permits only one collector-watchdog supervisor across scheduled and manual invocations.
- Collector `--trace-file` output is append-only and unbuffered; inspect the per-day trace after a watchdog restart before changing any liveness threshold.
- Watchdog spawns Binance collectors with `--trade-source rest`/`--mark-source rest` (fapi aggTrades/premiumIndex; spec 024 incident 08-04 — fstream silently drops aggTrade/markPrice/forceOrder from this egress) and hyperliquid collectors pure-WS (`trade_source=rest` requires a Binance normalizer)
- Collector watchdog validates `$Symbols` entries as `venue:SYMBOL` (lowercase alnum venue + uppercase alnum symbol; a plain `SYMBOL` means binance) and double-quotes them before spawn (anti-injection, audit 08-04)
- The collector watchdog, `start_collectors.ps1`, and the daily integrity pipeline (`scripts/daily_pipeline.ps1`) all derive their recording set from `core_symbols.txt` through ONE shared resolver, `scripts/recordings.ps1` (`Resolve-Recordings`, dot-sourced by all three — audit 08-10, after a hardcoded-binance heartbeat drift; invalid lines throw rather than silently narrowing the set) — keep recorded and required recordings in sync there, never as hand-maintained lists
- The storage-budget watch (OPS-15, `src/storage.rs` + `mp-ops storage-budget`) is corpus-derived and read-only: daily sizes come from the `{YYYYMMDD}_*.log` file names (W-6 — no state file; non-conforming names skipped; the current partial day excluded), the growth rate is a trailing-window mean daily addition rate (default 7 days), and `storage-budget` (P2) fires when the projection lands within the alert horizon (default 14 days) or the corpus is at/over the budget. The budget is explicit config (`--cap-bytes` or `MP_STORAGE_BUDGET_BYTES`) and an unconfigured budget fails closed (exit 2) — never a silent skip. Complements the current-usage `disk-high` (OPS-7): now vs projected. With `--manifest PATH` (Windows hook only — the VPS has no manifest) the watch ALSO fires when the relay is silently holding files: a drain-manifest entry whose LATEST per-file record is `action=landed` with `release` not in {released, no_release} (ssh_failed/skipped) — the byte-verified file never left the VPS; the verdict carries `held_vps_files`/`held_vps_count`. Fail-closed on an unreadable manifest. Daily cadence: `systemd/storage-budget.timer` (VPS) + best-effort hook in `daily_pipeline.ps1` (recording host).
- The Phase-0 gate is tolerance-based (2026-08-12): `is_clean()` = coverage ≥ 0.995 with no identity/provenance/`sequence_gap`/`backpressure_loss`/`low_coverage` findings; `stale_stream` and `coverage_gap` are warnings and `stale_bursts`/`worst_gap_ns` are margin fields surfaced in scorecards and `daily_pipeline.ps1` log lines (spec 024)
- The watchdog supervises `mp-whale` (spec 028 Hyperliquid on-chain census) alongside the market collectors via the same heartbeat/staleness model (`collectors/whale_positions.toml`); its log (`{date}_hyperliquid_positions.log`) feeds the liq-est band research edge (spec 029) and the whale.net/delta features (spec 016 materialization passes it to mp-materialize), and is not a required gate recording
- Deadman detection checks heartbeat files with configurable grace period
- Whale band-accuracy study runs weekly via `systemd/whale-study.timer` (Tue 06:30 UTC, clear of the Mon 06:00 grading run) → `scripts/run_whale_study_weekly.sh` → `research/run_band_accuracy.py`; the unit may write only `research/band_accuracy/` (weekly ledger + SIM-10 `runs/index.jsonl` tracker), RES-7 posture
- The daily promotion-gate verdict (`daily_pipeline.ps1`) is pushed to Telegram via `mp-ops telegram-send --id daily-pipeline --detail ... --severity p2|p3` (2026-08-10): one-shot, NO quiet-hours batching (the pipeline runs at 02:45 UTC, inside 22:00–07:00 — a batched P3 would sit until the next flush), fail-closed on missing creds (exit 2, WARN-only in the pipeline so the gate verdict/exit code is never masked by an alerting outage); non-promotable days send severity p2 with the per-recording DIRTY/blocking breakdown
- After the study, the wrapper runs the OPS-13 drift/decay watch: `mp-ops band-accuracy-decay --trend <out>/band_accuracy.jsonl --runs-dir /opt/money-printer/runs --telegram` (env `MP_OPS_CMD`, default `/opt/money-printer/bin/mp-ops`); the weekly verdict is journaled to `runs/index.jsonl` as a `band_accuracy_decay` record line (correlated to the study's run by `run_id`/`week`); best-effort — a missing binary skips, never fails the study
- The decay P3 is delivered via `src/telegram.rs` (the OPS-9 edge): the CLI routes it through `AlertRouter` (quiet hours from `MP_OPS_QUIET_START_MIN`/`END_MIN`, default 22:00–07:00 UTC), sends via curl to the Bot API (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`, `MP_OPS_TELEGRAM_URL` override, `disable_notification=true`), or batches into `journal/telegram/batch.jsonl`; `mp-ops telegram-flush --wait` waits out quiet hours internally (sleeping only while the window is active; `MP_OPS_SLEEP` stubs the sleeper in tests) then drains (fail-closed: a failed send keeps the batch and exits 2); each successful send is also appended to `journal/telegram/delivered.jsonl` (id + delivered_ts_ns, fsynced W-6 — the delivery log); the flush's batch-rewrite path (a failed send preserves the remaining ledger) is fsynced the same way (audit 2026-08-17), and curl transport-failure stderr is suppressed because it can embed the token-bearing Bot API URL (PD-2, audit 2026-08-17 — the response-body preview is kept: the Bot API never echoes the request URL); `load_telegram_batch`/`load_telegram_delivered` read the ledger pair (fail-closed, injected clock) for the monthly report's delivery-accountability section; `stale_batch_alert` raises `telegram-stale` (P2, OPS-14) when a dispatch sits queued ≥ one quiet window (default 24h — a missed flush), oldest wins, per-entity dedupe key — `mp-ops telegram-stale` runs it near-real-time (hourly `systemd/telegram-stale.timer`, P2 breaks through quiet hours)
- `src/report.rs` consumes `research/band_accuracy/band_accuracy.jsonl` (append-only, W-6): `load_band_accuracy_trend` grounds the monthly report's RES-4 section (OPS-6; missing journal = no-data month, corrupt line = fail closed); `band_accuracy_decay_alert` raises the `band-accuracy-decay` P3 on trailing-window drift (OPS-13, RES-3 semantics) — alert-only, never mutates the journal; `append_run_record` journals the weekly verdict to `runs/index.jsonl` (the RES-4 tracker, fsynced W-6)
- P1 webhook egress (owner decision 2026-08-06, audit 08-04 #3/#9): LIVE since 2026-08-09 — `MP_OPS_P1_WEBHOOK` is provisioned (user-level env) to an ntfy.sh secret topic (`https://ntfy.sh/<random-topic>`, topic name == the feed credential, embedded in the URL; the sink accepts the plain JSON POST with no auth headers). `mp-ops p1-webhook --id --detail` POSTs the P1 dispatch JSON to `MP_OPS_P1_WEBHOOK` via curl (https accepted, TLS is the host's) and fails loudly (exit 2, "dead until credentials") if the env var is ever unset. On a curl transport failure only the exit code is reported — stderr is suppressed (it can embed the token-bearing URL; audit 2026-08-08, PD-2)
